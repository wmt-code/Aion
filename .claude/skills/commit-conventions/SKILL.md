# 代码提交规范

## 格式

提交信息只写单行一句话，`scope` 必填：

```text
type(scope): 摘要
```

- `type`：小写英文类型，按实际变更目的选择。
- `scope`：必填，使用受影响的模块或领域名称，如 `auth`、`api`、`agent`、`docs`；优先沿用仓库现有命名，确实覆盖整个仓库时可用 `repo`。
- 使用英文半角括号和冒号，冒号后保留一个空格。
- 摘要默认使用简体中文，以“新增”“修复”“移除”“调整”等动作开头，说明具体变化；保留必要的技术名称。
- 标题保持单行、简短，不加句末标点；避免“更新代码”“修复问题”等无法辨识变更的描述。不为了缩短标题丢失关键语义。
- 不添加正文、页脚、AI 标签、生成工具署名、`Co-authored-by`、测试结果或其他附加信息。必要的变更事实直接写入这一句话。

## 类型

| type | 用途 |
| --- | --- |
| `feat` | 新增或扩展用户、调用方可用的功能 |
| `fix` | 修复错误行为 |
| `refactor` | 调整代码结构，不新增功能或修复错误 |
| `perf` | 改善性能 |
| `docs` | 修改文档 |
| `test` | 新增或调整测试 |
| `style` | 仅调整代码格式，不改变行为；界面样式变更按目的使用 `feat` 或 `fix` |
| `build` | 修改构建、打包或依赖 |
| `ci` | 修改持续集成、发布流水线 |
| `chore` | 不属于以上类型的维护事项 |
| `revert` | 回退已有提交 |

按主要目的选择类型。例如修复错误时附带测试，仍使用 `fix`；不要因包含测试而改用 `test`。

## 工单引用

- 当前任务有关联工单时，必须在摘要末尾用空格分隔并附上引用；没有关联工单时省略，不编造工单号或链接。
- 同仓库引用使用 `#工单号`，跨仓库引用使用 `组织名/仓库名#工单号`；以当前提交所在仓库判断是否跨仓库。
- 直接填写工单引用，不使用完整 URL 或 Markdown 链接；即使已知链接，同仓库仍写 `#1`，跨仓库写 `reling-mirror/a2a-java#147`。
- 多个关联工单用空格分隔，仍放在同一行末尾。

## 使用方式

- 以当前用户要求和目标仓库明确规则为准；历史提交用于参考命名，不自动覆盖本规范。
- 编写提交信息前检查目标仓库规则和实际差异。为即将提交的内容生成信息时，以暂存区差异为准；只提供了补丁或描述时，不推断未提供的改动。
- 一个提交表达一个清晰目的。无关改动建议拆分；必要的配套测试和文档可以随同提交。
- 用户只要求提交信息时，只返回提交信息这一行，不添加解释、前缀说明或代码围栏；没有差异或变更描述时，先获取内容，不编造提交事实。
- 技能本身不授权提交、推送、修改暂存区或重写历史。用户已明确要求的操作直接按既有授权执行，不重复请求确认；保留无关的工作区与暂存区改动。

## 示例

```text
ci(deploy): 构建 a2a-java Docker Compose 部署流程 #147
fix(api): 调整 Agent 调用参数 aion-harness/a2a-java#147
docs(readme): 补充本地启动步骤
```
